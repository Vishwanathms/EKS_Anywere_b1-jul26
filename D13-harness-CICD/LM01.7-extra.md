# PART 39 — Make a Change

This is where the lab becomes a **real CI/CD exercise**.

## Step 1 — Change the Replica Count

Open the Kubernetes deployment manifest:

```text
k8s/deployment.yaml
```

Change:

```yaml
replicas: 2
```

to:

```yaml
replicas: 3
```

---

## Step 2 — Commit the Change

Run:

```bash
git add .
git commit -m "Scale nginx to three replicas"
git push
```

---

## Step 3 — Run the Harness Pipeline

Go to the Harness pipeline:

```text
eks-anywhere-nginx-cd
```

Run the pipeline again using:

```text
Branch: main
```

Harness will:

```text
GitHub
   |
   | Updated deployment.yaml
   v
Harness Pipeline
   |
   v
Harness Delegate
   |
   v
EKS Anywhere
   |
   v
Kubernetes Deployment
   |
   v
3 NGINX Pods
```

---

## Step 4 — Verify the Pods

Run:

```bash
kubectl get pods -n harness-demo
```

Expected:

```text
NAME                            READY   STATUS
harness-nginx-xxxxx             1/1     Running
harness-nginx-yyyyy             1/1     Running
harness-nginx-zzzzz             1/1     Running
```

The actual Pod names will be different.

You can also verify the Deployment:

```bash
kubectl get deployment harness-nginx -n harness-demo
```

Expected:

```text
NAME            READY   UP-TO-DATE   AVAILABLE
harness-nginx   3/3     3            3
```

---

## What Students Have Demonstrated

Students have now demonstrated a complete GitOps-style deployment flow:

```text
Git Change
    ↓
GitHub
    ↓
Harness Pipeline
    ↓
Harness Delegate
    ↓
EKS Anywhere
    ↓
Kubernetes Deployment
    ↓
3 NGINX Replicas
```

# PART 40 — Rollback Exercise

Now demonstrate how a previous configuration can be restored through Git and the Harness pipeline.

## Step 1 — Change the Replica Count

Change:

```yaml
replicas: 3
```

back to:

```yaml
replicas: 2
```

---

## Step 2 — Commit and Push

Run:

```bash
git add .
git commit -m "Scale nginx back to two replicas"
git push
```

---

## Step 3 — Run the Harness Pipeline

Run:

```text
eks-anywhere-nginx-cd
```

Select:

```text
Branch: main
```

Then execute the pipeline.

---

## Step 4 — Verify the Deployment

Run:

```bash
kubectl get deployment harness-nginx -n harness-demo
```

Expected:

```text
NAME            READY   UP-TO-DATE   AVAILABLE
harness-nginx   2/2     2            2
```

Verify the Pods:

```bash
kubectl get pods -n harness-demo
```

Expected:

```text
NAME                            READY   STATUS
harness-nginx-xxxxx             1/1     Running
harness-nginx-yyyyy             1/1     Running
```

### Training Point

Students should understand that changing the Git manifest and re-running the pipeline can restore the desired configuration:

```text
3 Replicas
     ↓
Git Change
     ↓
Pipeline
     ↓
2 Replicas
```

> **Important:** This exercise demonstrates configuration rollback through Git. It is different from using Harness's native execution rollback or Kubernetes rollout history.

# PART 41 — Troubleshooting Lab

Give students a set of common troubleshooting scenarios.

The objective is to make students troubleshoot the problem instead of immediately recreating the environment.

---

## Scenario 1 — Delegate Not Appearing

Check the Delegate Pods:

```bash
kubectl get pods -n harness-delegate-ng
```

Example:

```text
NAME                                      READY   STATUS
eks-anywhere-delegate-xxxxxxxxxx          1/1     Running
```

If the Delegate Pod is not running, identify the Pod:

```bash
kubectl get pods -n harness-delegate-ng
```

Then describe it:

```bash
kubectl describe pod \
  -n harness-delegate-ng \
  <delegate-pod>
```

Check the Pod logs:

```bash
kubectl logs \
  -n harness-delegate-ng \
  <delegate-pod>
```

### Things to investigate

Students should look for:

* Pod scheduling failures
* Image pull failures
* Missing Secrets
* Configuration errors
* Authentication problems
* Network connectivity issues
* Resource constraints

---

# Scenario 2 — Delegate `CrashLoopBackOff`

Check the Delegate status:

```bash
kubectl get pods -n harness-delegate-ng
```

Example:

```text
NAME                                      READY   STATUS
eks-anywhere-delegate-xxxxxxxxxx          0/1     CrashLoopBackOff
```

Describe the Pod:

```bash
kubectl describe pod \
  -n harness-delegate-ng \
  <delegate-pod>
```

Check the logs:

```bash
kubectl logs \
  -n harness-delegate-ng \
  <delegate-pod>
```

If the container has restarted, previous logs can also be useful:

```bash
kubectl logs \
  -n harness-delegate-ng \
  <delegate-pod> \
  --previous
```

### Troubleshooting Flow

```text
Delegate CrashLoopBackOff
          |
          v
kubectl get pods
          |
          v
kubectl describe pod
          |
          v
kubectl logs
          |
          v
Identify Root Cause
```

---

# Scenario 3 — Test Internet Connectivity

The Harness Delegate needs appropriate outbound connectivity to communicate with Harness SaaS.

Start a temporary troubleshooting Pod:

```bash
kubectl run network-test \
  --image=curlimages/curl \
  --rm -it \
  -- sh
```

Inside the container, test connectivity:

```bash
curl -I https://app.harness.io
```

A successful response indicates that the Pod can reach the Harness endpoint.

Exit:

```bash
exit
```

The temporary Pod will be removed because `--rm` was specified.

---

# Scenario 4 — DNS Problem

Start a temporary DNS troubleshooting Pod:

```bash
kubectl run dns-test \
  --image=busybox \
  --rm -it \
  -- nslookup app.harness.io
```

A successful lookup should return the DNS resolution for:

```text
app.harness.io
```

If DNS resolution fails, investigate the Kubernetes DNS components:

```bash
kubectl get pods -n kube-system
```

Depending on the EKS Anywhere networking configuration, investigate CoreDNS and the underlying cluster networking.

---

# Scenario 5 — Kubernetes Deployment Problem

If the Harness pipeline succeeds but the application does not become ready, inspect Kubernetes events:

```bash
kubectl get events \
  -n harness-demo \
  --sort-by=.lastTimestamp
```

Also check:

```bash
kubectl get deployment -n harness-demo
```

Check the Pods:

```bash
kubectl get pods -n harness-demo
```

Describe a problematic Pod:

```bash
kubectl describe pod \
  -n harness-demo \
  <pod-name>
```

Check application logs:

```bash
kubectl logs \
  -n harness-demo \
  <pod-name>
```

### Troubleshooting Flow

```text
Harness Pipeline
       |
       v
Pipeline Failed?
       |
       +---- YES ---> Check Harness Execution
       |
       +---- NO
             |
             v
       Kubernetes Problem?
             |
             v
      kubectl get deployment
             |
             v
        kubectl get pods
             |
             v
      kubectl describe pod
             |
             v
        kubectl logs
             |
             v
      kubectl get events
```

# PART 42 — Very Important Security Exercise

> **Security Principle:** Do not teach students to use `cluster-admin` as the permanent production design.

For the first lab, the objective is:

```text
Make It Work
```

Once students understand the Harness → Delegate → Kubernetes flow, introduce:

```text
Least Privilege
```

---

## Current Lab Architecture

Initially, students may use broader permissions to simplify the first deployment exercise:

```text
Harness SaaS
      |
      v
Harness Delegate
      |
      v
ServiceAccount
      |
      v
Broad Kubernetes Permissions
      |
      v
EKS Anywhere
```

The purpose is to get the deployment working and understand the architecture.

---

# Production-Oriented Architecture

The production design should use only the permissions required by the deployment.

```text
Harness Delegate
       |
       v
ServiceAccount
       |
       v
Role / ClusterRole
       |
       v
RoleBinding / ClusterRoleBinding
       |
       v
Only Required Kubernetes Permissions
```

---

## Least-Privilege Example

For a simple NGINX deployment, the application may require permissions such as:

### Deployments

```yaml
deployments:
  - get
  - list
  - create
  - update
  - patch
```

### Services

```yaml
services:
  - get
  - list
  - create
  - update
  - patch
```

### Pods

```yaml
pods:
  - get
  - list
```

These permissions are only an **example starting point**.

> The exact permissions should be narrowed according to what the Harness pipeline actually performs.

---

## Security Exercise — Student Objective

Ask students to compare:

### Approach 1 — Broad Access

```text
Harness Delegate
      |
      v
ServiceAccount
      |
      v
cluster-admin
      |
      v
Entire Cluster
```

versus:

### Approach 2 — Least Privilege

```text
Harness Delegate
      |
      v
ServiceAccount
      |
      v
Role / ClusterRole
      |
      v
Only Required Resources
      |
      v
Only Required Actions
```

### Key Takeaway

```text
Development Lab
      ↓
Make it work
      ↓
Understand the architecture
      ↓
Identify required permissions
      ↓
Apply least privilege
      ↓
Production-ready design
```

**Production rule:** Avoid giving the Harness Delegate `cluster-admin` unless there is a specific, justified requirement for cluster-wide administrative operations.
