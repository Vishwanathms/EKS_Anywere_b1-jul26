This is actually an excellent production enhancement. Before moving to Kustomize, let's make the **Helm chart production-ready** by adding **Horizontal Pod Autoscaler (HPA)**.

The architecture will become:

```text
gitops-nginx
└── helm
    └── nginx-demo
        ├── Chart.yaml
        ├── values.yaml
        └── templates
            ├── deployment.yaml
            ├── service.yaml
            ├── ingress.yaml
            ├── hpa.yaml          <-- NEW
            └── _helpers.tpl
```

---

# Step 1 - Verify Metrics Server

HPA requires the Kubernetes Metrics Server.

Verify it is installed:

```bash
kubectl get deployment metrics-server -n kube-system
```

Verify metrics are available:

```bash
kubectl top nodes

kubectl top pods
```

If these commands return CPU and memory usage, HPA will work.

---

# Step 2 - Update values.yaml

Add the following section to your existing `values.yaml`.

```yaml
company: Vishwacloudlab

application: GitOps Demo

environment: DEV

version: v1.0

color: blue

replicas: 2

namespace: gitops-helm

image:
  repository: nginx
  tag: latest
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

ingress:
  enabled: true
  className: nginx
  host: nginx.demo.local
  path: /
  pathType: Prefix

#############################################
# NEW HPA CONFIGURATION
#############################################

autoscaling:
  enabled: true

  minReplicas: 2

  maxReplicas: 6

  targetCPUUtilizationPercentage: 50

  targetMemoryUtilizationPercentage: 70
```

---

# Step 3 - Add Resource Limits

HPA **will not function correctly** unless CPU requests are defined.

Modify your `deployment.yaml`.

Replace the container section with:

```yaml
containers:

- name: nginx

  image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

  imagePullPolicy: {{ .Values.image.pullPolicy }}

  ports:

  - containerPort: 80

  resources:

    requests:

      cpu: "100m"

      memory: "128Mi"

    limits:

      cpu: "500m"

      memory: "256Mi"

  env:

  - name: COMPANY
    value: "{{ .Values.company }}"

  - name: APPLICATION
    value: "{{ .Values.application }}"

  - name: ENVIRONMENT
    value: "{{ .Values.environment }}"

  - name: VERSION
    value: "{{ .Values.version }}"

  - name: COLOR
    value: "{{ .Values.color }}"
```

> **Why?** HPA calculates utilization as a percentage of the **requested CPU**, so CPU requests are mandatory.

---

# Step 4 - Create hpa.yaml

Create a new file:

```
templates/hpa.yaml
```

Add:

```yaml
{{- if .Values.autoscaling.enabled }}

apiVersion: autoscaling/v2

kind: HorizontalPodAutoscaler

metadata:

  name: {{ include "nginx-demo.fullname" . }}

  namespace: {{ .Values.namespace }}

spec:

  scaleTargetRef:

    apiVersion: apps/v1

    kind: Deployment

    name: {{ include "nginx-demo.fullname" . }}

  minReplicas: {{ .Values.autoscaling.minReplicas }}

  maxReplicas: {{ .Values.autoscaling.maxReplicas }}

  metrics:

  - type: Resource

    resource:

      name: cpu

      target:

        type: Utilization

        averageUtilization: {{ .Values.autoscaling.targetCPUUtilizationPercentage }}

  - type: Resource

    resource:

      name: memory

      target:

        type: Utilization

        averageUtilization: {{ .Values.autoscaling.targetMemoryUtilizationPercentage }}

{{- end }}
```

# Step 9 - Generate Load

Since your application is NGINX, create a temporary load generator:

```bash
kubectl run load-generator \
  --rm -it \
  --image=busybox \
  --restart=Never \
  -- /bin/sh
```

Inside the container:

```sh
while true
do
    wget -q -O- http://nginx-demo.gitops-helm.svc.cluster.local
done
```

Leave it running.

---

# Step 11 - Stop the Load

Press **Ctrl+C** in the BusyBox container or exit the shell.

After a stabilization period (typically around 5 minutes with default Kubernetes settings), the HPA will gradually scale the deployment back down toward the minimum replica count.

# Production Improvements (Recommended)

For a production-grade Helm chart that mirrors enterprise deployments, I recommend making these additional enhancements before moving to Kustomize:

1. Make `resources.requests` and `resources.limits` configurable in `values.yaml` instead of hardcoding them.
2. Add HPA behavior settings (`scaleUp` and `scaleDown` policies) to control scaling speed.
3. Add configurable liveness and readiness probes.
4. Add configurable node selectors, tolerations, and affinity rules.
5. Add PodDisruptionBudget (PDB) support.
6. Add optional ServiceMonitor support for Prometheus.

These additions will make the chart closely resemble what students encounter in real production GitOps repositories and provide a stronger foundation before introducing Kustomize.
