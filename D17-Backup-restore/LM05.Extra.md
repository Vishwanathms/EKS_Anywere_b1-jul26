

# Part 18 – Important EKS Anywhere Discussion

This is where I would make the lab different from a normal Kubernetes Velero lab.

### EKS Anywhere has multiple layers

```text
                 EKS Anywhere
                      |
        +-------------+-------------+
        |                           |
 Cluster Lifecycle            Application Layer
        |                           |
 CAPI / EKS-A                 Kubernetes objects
 vSphere                      Deployments
 Control Plane                Services
 Worker Nodes                 ConfigMaps
                              Secrets
                                   |
                                  PVC
                                   |
                              vSphere CSI
                                   |
                              vSphere Storage
```

Velero is primarily addressing the **application/workload recovery layer**.

It is **not a replacement for EKS Anywhere cluster lifecycle management**.

EKS Anywhere's own documentation distinguishes cluster lifecycle operations such as create, update, upgrade, scale and delete from workload management. ([EKS Anywhere][5])

# Part 19 – Very Important: Backup ≠ Full EKS Anywhere Cluster Backup

I would explicitly teach students this distinction.

### Velero backup

```text
Kubernetes Resources
        +
Application Data
        ↓
      Velero
```

### EKS Anywhere infrastructure

```text
vCenter
   |
ESXi
   |
VMs
   |
Control Plane
Worker Nodes
```

Velero does **not** mean:

> "I can delete my entire EKS Anywhere vSphere infrastructure and recreate everything with one Velero restore."

For a real disaster recovery design, you need to consider:

* EKS Anywhere cluster configuration
* cluster YAML
* kubeconfig
* vSphere infrastructure
* vSphere Content Library
* VM infrastructure
* CSI/storage
* Kubernetes objects
* application data
* external dependencies

EKS Anywhere specifically recommends retaining the admin-machine artifacts such as the kubeconfig, SSH keys and cluster specification because they are required for subsequent lifecycle operations. ([EKS Anywhere][6])

# Part 20 – Advanced Lab: Restore Only Namespace

Create another namespace:

```bash
kubectl create namespace restored-demo
```

You can demonstrate selective restoration by restoring into a different namespace:

```bash
velero restore create restored-demo \
  --from-backup backup-demo \
  --namespace-mappings backup-demo:restored-demo
```

Verify:

```bash
kubectl get all -n restored-demo
```

And:

```bash
kubectl get pvc -n restored-demo
```

Then verify the data.

This demonstrates **migration / cloning**, not just disaster recovery.

Velero explicitly supports using backups to migrate resources between clusters and replicate production environments to development/testing. ([Velero][2])

# Part 21 – Advanced Lab: Backup Entire Cluster

Once the namespace exercise works:

```bash
velero backup create eks-anywhere-full
```

Check:

```bash
velero backup describe eks-anywhere-full --details
```

Students should inspect the resources captured.

You can then discuss:

### What gets backed up?

```text
Deployments
Services
ConfigMaps
Secrets
Namespaces
RBAC
PVCs
PV metadata
CRDs
Custom Resources
Pod volume data
```

### What doesn't automatically become a complete infrastructure backup?

```text
vCenter
ESXi
VMs
Content Library
EKS-A cluster YAML
Admin machine
External databases
External load balancers
External DNS
```

# Part 22 – CSI Snapshot Discussion

Because your EKS Anywhere environment is on **vSphere**, this is also a good opportunity to introduce CSI snapshots.

Velero supports Kubernetes CSI snapshot APIs when the cluster's CSI driver supports the required snapshot functionality. From Velero 1.14 onward, the CSI functionality is integrated into Velero, so the old separate Velero CSI plugin is no longer required. ([Velero][7])

Show:

```bash
kubectl get volumesnapshotclass
```

If available:

```bash
kubectl get volumesnapshot -A
```

And:

```bash
kubectl get volumesnapshotcontent
```

Then explain the two approaches:

| Method                       | EKS Anywhere lab                                |
| ---------------------------- | ----------------------------------------------- |
| Kubernetes object backup     | ✅                                               |
| File System Backup           | ✅ Recommended for this lab                      |
| CSI Snapshot                 | ✅ If vSphere CSI snapshot support is configured |
| S3/MinIO backup repository   | ✅                                               |
| vCenter VM snapshot          | Separate mechanism                              |
| Full EKS-A infrastructure DR | Separate DR design                              |

# Final Student Challenge

After completing the guided lab, give students this scenario:

> **Scenario:**
> A production application called `booking-app` is running on EKS Anywhere. It has a Deployment, Service, ConfigMap, Secret and a 10 GB PVC containing application data.
>
> At 2:00 PM the namespace is accidentally deleted.
>
> Your task is to recover the application using Velero.

### Student must demonstrate

```text
[ ] Identify the failed namespace
[ ] Identify the latest Velero backup
[ ] Inspect backup contents
[ ] Restore namespace
[ ] Restore PVC
[ ] Verify PV binding
[ ] Verify application pod
[ ] Verify application service
[ ] Verify application data
[ ] Verify ConfigMap
[ ] Verify Secret
[ ] Demonstrate application functionality
```

## Recommended placement in your EKS Anywhere 16-day course

I would position this as:

### **Module – Day 12/13: Backup, Recovery & Disaster Recovery**

**Theory – 1.5 hrs**

* Backup vs Snapshot vs Replication
* Velero architecture
* Backup Storage Location
* Volume Snapshot Location
* File System Backup
* CSI snapshots
* Kubernetes object backup
* PV/PVC backup
* EKS Anywhere DR considerations
* RPO / RTO
* Application-level vs infrastructure-level recovery

**Lab – 2.5 hrs**

```text
1. Prepare MinIO                         20 min
2. Install Velero                        20 min
3. Configure backup storage              20 min
4. Deploy stateful application           20 min
5. Create backup                         15 min
6. Verify PV backup                      15 min
7. Simulate namespace disaster           10 min
8. Restore namespace                     20 min
9. Verify PV + application data          15 min
10. Selective namespace restore           15 min
```

This makes the lab much more valuable than simply teaching `velero backup create`.

**One important recommendation for your specific training environment:** since all students share the same vSphere infrastructure and you are using a shared environment, give each student a **unique MinIO bucket/prefix and unique namespace**, for example `student01/velero`, `student02/velero`, etc. That prevents one student's Velero backup/restore exercise from interfering with another student's lab.
