# Lab — Harness CD: Git-Driven Deployment Using Pipeline-as-Code

## Module 9 — Harness CD

### Lab Objective

In this lab, students will extend their existing Harness knowledge and build a **Git-driven Continuous Delivery pipeline** for an existing Python + Redis application.

The application Kubernetes manifests are already available in GitHub.

The objective is to demonstrate:

```text
Change Kubernetes Manifest
          ↓
       git push
          ↓
    GitHub Webhook
          ↓
     Harness Trigger
          ↓
    Harness CD Pipeline
          ↓
       Delegate
          ↓
     EKS Anywhere
```

The student should **not manually run the Harness pipeline** after the initial setup.

# 3. Create the Harness CD Pipeline

Create:

```text
Project
 → Deployments
 → Pipelines
 → Create Pipeline
```

Pipeline name:

```text
python-redis-cd
```

Open the pipeline in **YAML mode**.

The pipeline should contain:

```text
Deployment Stage
       |
       +-- Service
       |
       +-- Environment
       |
       +-- Kubernetes Infrastructure
       |
       +-- Rolling Deployment
       |
       +-- Rollback
```

Harness Kubernetes CD uses deployment stages with a Kubernetes deployment strategy such as Rolling.

---

# 4. Configure the Service

Create:

```text

python-redis
```

```text
Deployment Type:
Kubernetes
```

Configure:

```text

Repository: <student-python-redis>
Branch: main
Manifest Path: manifests/
```

Use:

```text
Latest from Branch
```

This is important.

Harness will fetch the **latest version of the manifests from GitHub whenever the pipeline executes**.

Conceptually:

```text
Harness Pipeline
       |
       v
GitHub
       |
       v
Latest manifests
       |
       v
EKS Anywhere
```

# 9. Create the GitHub Push Trigger

Open:

```text
Pipeline
 → Triggers
 → New Trigger
```

Select:

```text
GitHub
```

Event:

```text
Push
```

Repository:

```text
student-python-redis
```

Branch:

```text
main
```

Harness supports GitHub push events as pipeline triggers.

---

# 10. Restrict the Trigger to Manifest Changes

Configure the trigger so that it runs only when files under:

```text
manifests/
```

change.

Conceptually:

```text
GitHub Push
     |
     v
Branch = main?
     |
    YES
     |
     v
Did manifests/ change?
     |
    YES
     |
     v
Run Harness Pipeline
```

Harness supports changed-file conditions for Git triggers.

This is an important production concept.

We do **not** want:

```text
README change
     ↓
Deployment
```

We want:

```text
Deployment manifest change
     ↓
Deployment
```

# 19. Key Learning

Students should leave the lab understanding:

```text
Git
 ↓
Event
 ↓
Pipeline
 ↓
Deployment
 ↓
Verification
 ↓
Rollback
```

The critical concept is:

> **Harness is not simply being used as a button to deploy Kubernetes YAML.**

The Git repository becomes the source of the deployment change, and the GitHub event automatically starts the Harness CD pipeline.
