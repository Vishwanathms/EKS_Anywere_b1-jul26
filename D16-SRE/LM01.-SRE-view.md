# Module 13 Lab — EKS Anywhere Platform SRE

## Lab Scenario

Students are acting as **Platform SRE engineers** responsible for an EKS Anywhere cluster.

They will deliberately introduce four different failure conditions:

1. **Pod Failure**
2. **Node Failure**
3. **Resource Pressure**
4. **Alert Testing**

For every incident, students follow the same SRE process:

```text
Observe
   ↓
Detect
   ↓
Triage
   ↓
Diagnose
   ↓
Mitigate
   ↓
Recover
   ↓
Verify
   ↓
Document
```

## Objective

Students learn:

* Pod failure detection
* Pod troubleshooting
* Logs
* Events


**Why did Kubernetes create a new pod?**

Expected concept:

```text
Deployment
     ↓
ReplicaSet
     ↓
Desired replicas = 3
     ↓
Actual replicas = 2
     ↓
Create replacement Pod
```

## Step 4 — Look at events


Students document:

* What failed?

# Incident 2 — Node Failure

Now increase the severity.

Instead of killing a pod, students simulate a **worker-node failure**.

## Important safety rule

**Do NOT shut down the control-plane VM or manipulate the production EKS Anywhere control plane.**

Use a **worker node only**, preferably a dedicated worker node created for this lab.

Power the worker VM back on from vCenter.


## SRE checkpoint

Students answer:

> **What is the difference between recovering a pod and recovering a node?**

Expected:

```text
Pod failure
→ Kubernetes recreates workload

Node failure
→ Infrastructure must recover
→ Kubernetes can reschedule workloads
```

This is a **very important EKS Anywhere distinction**.

## One important EKS Anywhere teaching point

I would explicitly emphasize this throughout the lab:

```text
                 EKS Anywhere SRE
                        │
        ┌───────────────┴────────────────┐
        │                                │
 Kubernetes Layer                  Infrastructure Layer
        │                                │
 Pods                               VM
 Deployments                        ESXi
 Services                           vCenter
 Nodes                              Datastore
 CNI                                Network
 API Server                         Compute
 etcd                               Storage
        │                                │
        └───────────────┬────────────────┘
                        ↓
                  Application SLA
```

**This is what makes the EKS Anywhere SRE lab different from a normal Kubernetes troubleshooting lab.**

Students should learn that when a Kubernetes node goes `NotReady`, the investigation doesn't necessarily stop at `kubectl`. They need to be comfortable moving **from Kubernetes → EKS Anywhere → VM → vSphere → ESXi → network/storage**, which is exactly the platform-SRE skill you want them to demonstrate.
